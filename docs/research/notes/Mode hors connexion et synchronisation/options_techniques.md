# Offline editing with later resync for a Flutter client on a REST backend: implementation options and tooling (state at 2026-11-25)

Context for the report writer: one-developer "year in pixels" tracker. Backend Express + PostgreSQL on a single 1-vCPU VPS (the traffic-measurement notes in this folder's sibling, `Mesure de trafic auto hébergée/outils_open_source.md`, record ~950 MB RAM with ~490 MB free on 2026-11-23), REST plus a WebSocket that pushes changes to the user's other devices. Data: tracker pages (server-generated UUIDs), legends per page (server-generated UUIDs; colour + label, ordered), cells keyed naturally by (page_id, year, month, day) with colour + optional comment. From the lead's reading of the code [CODE]: the client keeps a JSON snapshot of the last bootstrap (pages, legends, cells of the active year only) and paints from it at cold start; an offline session stays logged in on stored tokens; writes are optimistic with a 20 s REST timeout and are silently reverted on any failure; there is no queue, so an offline edit disappears; the server upserts cells unconditionally (INSERT … ON CONFLICT DO UPDATE, updated_at = server now()), deletes are hard deletes (no tombstones), a "recolor" endpoint rewrites colours across all of a page's cells, pages/legends are created by POST with server-generated ids; re-fetch on app resume and on WebSocket reconnect. Conflict rules and user expectations are covered by other researchers; this file covers implementation options and tooling.

## Q1. What the official Flutter and Android guides recommend for this exact case

### Takeaway
Both guides describe the same three write strategies: online-only writes (block or disable editing when offline), a queue, and "write locally first then sync" (a `synchronized` flag in Flutter, "lazy writes" in Android). Android is explicit that lazy writes are the right choice when user data is critical, that the local store should be the single source of truth, that "last write wins" with timestamps is the common mobile conflict rule, and that draining the queue is WorkManager work. The Flutter page suggests a periodic `Timer`, `workmanager`, `connectivity_plus` and push messages, and says nothing about conflicts.

## Q2. Option (a): read-only offline cache of the last state, made robust

### Takeaway
The app already has most of (a). What it lacks to be robust is coverage (all years, not only the active one), an honest "offline" signal derived from real request failures rather than from `connectivity_plus`, and replacing the silent revert with an explicit "you are offline, editing is paused" state. No backend change is needed; it is days of client work.

### Inferences
- [INFERENCE] Robust (a) for this app = (1) snapshot all years of every page (cells are tiny: at most 366 per page-year), ideally one file per page-year or a small SQLite table, written atomically (write temp file then rename); (2) an "offline" state set when a request fails with a socket error/timeout or the WebSocket cannot connect, cleared on the next successful request or WS open, with `connectivity_plus` used only as a hint to retry sooner; (3) when offline, cells are tappable to read but the colour picker is disabled with a message, instead of the current optimistic-then-silent-revert path (which today makes an offline edit look accepted, then vanish); (4) a "last synced at" stamp. Backend: none, except optionally a cheap health endpoint for the reachability check. — based on https://pub.dev/packages/connectivity_plus ; https://developer.android.com/topic/architecture/data-layer/offline-first, read 2026-11-25
- [INFERENCE] The 20 s timeout is long for detecting "offline" on a tap; a short connect timeout plus the offline flag avoids users waiting 20 s for a revert. — based on the lead's [CODE] brief and https://pub.dev/packages/connectivity_plus, read 2026-11-25

## Q3. Option (b): optimistic writes with a persistent on-device outbox, replayed when the network returns

### Takeaway
This is the pattern both official guides describe ("lazy writes"), and indie/team reports converge on the same recipe: write the local change and the outbox entry in one SQLite transaction, drain in order with backoff, classify errors (retry network/408/429/5xx, park 4xx), and make the server idempotent. For this app the cell upsert on a natural key is already replay-safe; pages and legends created offline are not, because their ids are server-generated. Background replay is realistic on Android (WorkManager with a network constraint) but only best-effort on iOS (system-scheduled, typically about once a day, never after a force-quit), so replay should be designed as foreground-first (start, resume, WebSocket reconnect, after any successful request), with background as a bonus.

## Q4. Option (c): full local-first database on device with a custom pull/push protocol

### Takeaway
Here the device database (drift on SQLite in practice) becomes the source of truth for pages, legends and cells, the UI watches it, and a sync loop pushes a mutation log and pulls "changes since cursor". It removes the need for snapshots and overlays, but the server must grow change tracking it does not have today: a monotonic change cursor, tombstones for deletes, and per-client mutation ids. drift is the most mature Flutter tool for the local side; its maintainer explicitly does not plan to ship sync. Weeks of work plus permanent maintenance of a protocol.

## Q5. Option (d1): PowerSync (Flutter SDK + Postgres logical replication; writes through your own API)

### Takeaway
PowerSync is the most mature Flutter-first sync engine in late 2026: a verified-publisher Dart SDK on SQLite, the server service streaming from Postgres logical replication, and writes going back through a connector that calls your own REST API. On 2026-11-03 the self-hosted service moved from FSL to Apache-2.0. It needs `wal_level = logical`, a replication role and publication, single text `id` columns (client-generated UUIDs; composite keys concatenated), and either the Cloud (Free tier 50 peak clients and deactivation after inactivity; Pro from $49/month) or a self-hosted service whose smallest documented footprint (1 vCPU, 512 MiB for the service plus a bucket-storage database) does not fit in ~490 MB free on the current VPS.
