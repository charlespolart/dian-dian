# Offline writes for a one-cell-per-day tracker: conflict rules, outbox pitfalls, and what teams that added offline late report

Context for the report writer: a one-developer "year in pixels" tracker. Flutter client (iOS first); Express + PostgreSQL on one VPS; REST plus a WebSocket that pushes changes to the user's other devices. Tracker pages and legends have server-generated UUIDs; cells are keyed naturally by (page_id, year, month, day) and hold a colour and an optional free-text comment (a short diary entry). The owner proposes: "when a change is waiting to be synchronised and the remote state has changed, keep the remote state; the local change is dropped." These notes test that rule against the alternatives, list queue pitfalls with what the reference write-ups recommend, and collect what teams that added offline support late reported.

## Q1. The owner's rule against the alternatives; what "the remote state has changed" requires; the simplest rule that never silently loses a diary entry; granularity and coarse operations

### Takeaway
The owner's rule is "first writer to reach the server wins" and it can only be implemented as compare-and-set: each queued edit must carry the version of the cell it was based on, and the server (or the client before sending) must compare it with the current one. Every LWW variant, the owner's rule included, silently discards one of two concurrent values; the literature (Kleppmann, Apple's WWDC19 talk, Joplin, CouchDB, CloudKit) converges on one point: for free text you either merge or keep both. The simplest rule that never silently loses a diary entry is compare-and-set per cell with "server wins" for the colour and "keep both" for a differing, non-empty comment (a conflict copy). Conflicts need the same day of the same tracker edited on two devices while one is offline, which is rare; the coarse operations (recolor across all years, which also bumps `updated_at` on every matching cell, legend reorder/delete, year reset, page delete) are where any rule has to be decided separately.

### Cited Findings

**What LWW loses, and why clocks make it worse**
- [COMMENTARY] Martin Kleppmann's Cambridge lecture notes (Distributed Systems, Michaelmas 2021/22, Slide 95): last writer wins "Keep v2 and discard v1 if t2 > t1. Note: data loss!"; with LWW "any concurrent updates with lower timestamps to the same key are discarded. This approach is simple to work with, but it does imply data loss … in some systems, discarding concurrent updates is fine." The alternative is a multi-value register: with partially ordered timestamps (vector clocks), concurrent values are all kept ("conflicts, or sometimes siblings") and merged later by the application — https://www.cl.cam.ac.uk/teaching/2122/ConcDisSys/dist-sys-notes.pdf, read 2026-11-25
- [COMMENTARY] Same notes (Slide 140, p. 77), a calendar example that maps directly onto colour-vs-comment: one device changes an event's time, another its title; after sync "the update of the time is applied to both devices, while the update of the title is discarded … at the cost of a small amount of data loss. This is the last writer wins approach … A more refined approach might merge the updates to the time and the title" — https://www.cl.cam.ac.uk/teaching/2122/ConcDisSys/dist-sys-notes.pdf, read 2026-11-25
- [COMMENTARY] Same notes (pp. 30–31) on device clocks: NTP slews small skews, "steps" larger ones so applications "see time suddenly jump forwards or backwards", and if the skew is very large (by default more than about 15 minutes) the NTP client "may decide that something must be wrong, and refuse to adjust the clock"; "just because a node is running NTP, that does not guarantee that its clock will be correct" — https://www.cl.cam.ac.uk/teaching/2122/ConcDisSys/dist-sys-notes.pdf, read 2026-11-25
- [COMMENTARY] Kyle Kingsbury (aphyr, 12 Oct 2013), "The trouble with timestamps": timestamps "as implemented in Riak, Cassandra, et al, are fundamentally unsafe ordering constructs"; "Even when perfectly synchronized, POSIX time itself is not monotonic"; a write with a smaller timestamp "isn't just temporarily invisible; it's gone forever"; "NTP does not solve it for you". A delete tombstone carrying a far-future timestamp can destroy "every write to a record for days to weeks afterwards". He prefers "Higher latencies or client-side exceptions" over "silently lost data" — https://aphyr.com/posts/299-the-trouble-with-timestamps, read 2026-11-25
- [DOCS] Android's offline-first guide presents "last write wins" as "a common approach" for mobile apps: "devices attach timestamp metadata to the data they write … the network data source … discards any data older than its current state". Its example orders two offline devices by the time each wrote — i.e. device clocks. The page does not discuss clock skew, user-changed clocks or text merges — https://developer.android.com/topic/architecture/data-layer/offline-first, read 2026-11-25

**Hybrid logical clocks**

**Compare-and-set (version / ETag) and what "the remote changed" requires**

## Q2. Two concrete scenarios for the owner's rule

### Takeaway
The owner's rule fails exactly where the offline edit is the valuable one and the remote change is trivial or incidental (a quick colour tap, a recolor that bumped `updated_at`): the diary text written offline is dropped. It is clearly right where the remote change is deliberate and newer than the device's stale queue (a tracker deleted or a day corrected on another device while an old device sat offline), which is where today's arrival-order LWW gets it wrong.

**Scenario 2 — the rule is clearly right**
- [INFERENCE] Setup: an old iPad stays in a drawer, offline, with a queue from 2 March: the user had coloured 1 March "sick" and written "flu?". ## Q3. Outbox / offline-queue pitfalls and what the write-ups recommend

### Takeaway
Every write-up that built a queue says the hard part is not conflicts but getting each change through exactly once, in order, and knowing when to give up: idempotency keys (client UUIDs, Todoist's `uuid` + `temp_id`, the IETF draft), per-entity ordering, a strict temporary-vs-permanent error split so one poisoned item cannot wedge the queue, a cap or expiry, and visible state for the user. Cells are naturally keyed, so the duplicate problem here is limited to creating pages and legends offline; the riskiest items for this app are a 401/expired token being treated as a permanent failure, parents deleted elsewhere, and logout with pending edits.

## Q4. What the reference write-ups say

### Takeaway
Neutral platform docs are thin on conflicts: Android names LWW by device timestamp as "a common approach" and stops there; Flutter's page does not cover conflicts at all; Apple's CloudKit gives the primitives for compare-and-set and three-way merge, while NSPersistentCloudKitContainer silently applies LWW. The production write-ups (Figma, Trello, Linear, Actual, Todoist, CouchDB) all use a server-authoritative order with LWW at some granularity, plus client-generated ids or per-command UUIDs; the ones that discuss free text (Apple, Trello, Kleppmann) say LWW is where it hurts.

## Comparison of conflict rules

| Rule | What it needs | Loses data when | Right when | Complexity |
|---|---|---|---|---|
| LWW by server arrival (today) | Nothing (unconditional upsert) | A stale or late device's replay overwrites a newer edit, comment included; a colour-only PUT clears a comment; a late edit recreates a cell deleted elsewhere; a replay after a recolor writes the old colour back | Edits are rare and devices mostly online; fields of low value | None |
| Owner's rule: remote wins if changed (compare-and-set, drop local) | Base version per queued edit, kept apart from the optimistic `updated_at`; server precondition (If-Match / body field, 412 + current row); a version that the recolor does not bump needlessly | The dropped local edit is the valuable one (offline diary text vs a remote colour tap or recolor); both devices create the same day's cell | The remote change is newer and deliberate (correction, page deleted) and the local queue is stale; colour-only conflicts | Low–medium |
| LWW by client timestamp | Device timestamp in each op; server compares | Clock skew, a user-changed clock, NTP steps, time-zone or serialization bugs reorder edits; a far-future clock wins "for days" | Clocks trusted and fields low-value | Low, but bugs are subtle |
| LWW by HLC | HLC per device; server keeps the max; drift rejection (Actual: 1 minute) | Still LWW: concurrent edits to the same field lose one value; a client outside the drift window is refused | Many writers need an order close to wall time with causality | Medium |
| Per-field LWW (colour vs comment) | Field-level PATCH (or `changedKeys`-style partial writes) with per-field versions/timestamps | Same field edited on two devices | Different devices changed different fields | Low–medium |
| Compare-and-set + ask the user | Base version; conflict UI; 412 handling | User dismisses or chooses wrongly; UI never seen if the app is in the background | Rare, high-value conflicts | High for one developer (UI, states) |
| Compare-and-set, server wins for colour, keep both for a differing non-empty comment (conflict copy) | Base version; a place for the conflict copy (column or appended text); a one-time notice | Never loses text; may duplicate it; colour of the losing device dropped | Diary text must never vanish; conflicts rare | Medium |
| No version, "never shrink a comment" on replay | A flag on replayed ops; server merge rule (empty → take other, both differ → concatenate) | Never loses text; may duplicate it or bring back a comment deliberately cleared offline | Simplest protection for text | Low |
| Operation log + server-authoritative replay (Replicache, Linear) | Client mutation ids, ordered durable log, server mutators, rebase of pending ops on pull, push/schema versions | Whatever the mutator decides; a poison mutation blocks the client unless skipped | Many operation types and invariants (lists, reorders) | High |
| CRDT (Actual's LWW map + HLC; Automerge for text) | CRDT library or message log, merkle/sync protocol, tombstones, compaction, schema migration of messages | LWW-map: same as per-field LWW; text CRDTs merge characters (can interleave) | Peer-to-peer or long offline collaboration | High |
| Tombstones for deletes (orthogonal) | `deleted_at` rows or a change log; garbage collection | Without them: deletes resurrected by late edits under LWW; incremental pull cannot report deletions | Any delta sync, "delete wins" rule, or recovery | Low–medium |
