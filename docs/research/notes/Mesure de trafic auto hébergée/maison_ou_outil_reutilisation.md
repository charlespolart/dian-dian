# Self-hosted traffic measurement: home-made counter or open-source tool, store-click and install attribution, reuse across projects

Context for the report writer: Dian Dian is a one-developer indie app. Its single landing page is rendered server-side by an Express (TypeScript) backend behind Caddy, with PostgreSQL 16, in Docker, on a 1 vCPU / ~1 GB RAM VPS. Backups are pgBackRest to R2 (PITR). The landing already maps utm_source / utm_campaign to App Store campaign tokens (pt/ct) and to Google Play `referrer` parameters on the store buttons. The wish list is visits, daily unique visitors, source, referring site, device, in-app browser, country, store-button clicks, and bots (AI bots by name), with no consent banner. The repo already holds a spec that picks the home-made counter (`docs/superpowers/specs/2026-11-23-landing-visits-design.md`, approach 1 "retenu (Charles, 2026-11-23)"). These notes test that choice against adopting a tool, and cover attribution and reuse.

Research done 2026-11-23. Evidence labels:

- [CODE]: the tool's source code on GitHub, read in this session.
- [REGISTRY]: npm, pub.dev or GitHub API metadata (versions, dates, licences, stars), queried in this session.

## Q1. Indie developers who built minimal home-made analytics vs adopted Umami / GoatCounter / Plausible, what they reported later, and whether any minimal Node/Express server-side analytics library is maintained in 2026

### Takeaway
Home-made, server-side counters are a known indie pattern (Bear Blog's hit-counter is the clearest example: bot user-agents dropped, IP hashed with the date for daily uniques, hashes scrubbed daily). Long-term reports on self-hosted tools are mixed: one blogger left self-hosted Umami after 3+ years because both upgrades failed, another kept Umami after trying GoatCounter, Ackee, counter.dev and Plausible, and found Plausible's 2 GB+ RAM "a bit steep". There is no maintained, generic "server-side analytics" Express middleware on npm in 2026; the official Umami Node client was last published in August 2024. What is maintained are the building blocks: `isbot`, the `ai.robots.txt` crawler list, `crawler-user-agents`, `bowser`, and `ua-parser-js` (now AGPL-3.0 in v2).

### Cited Findings

**Home-made examples**
- [AUTHOR] Bear Blog (Herman Martinus, 1 Nov 2023) counts reads without client JavaScript: CSS on `body:hover` fires a request to a hit endpoint; the server "discards requests that match a bot user-agent", derives the country from the IP, extracts browser and platform, then hashes the IP with the date so repeat requests from the same IP on the same day count once. "A background task which runs at the end of each day" scrubs the hashes. He knows "many great open-source, privacy-focussed analytics platforms" exist but wanted something native, and notes "Even Fathom and Plausible analytics struggle with logging activity on adblocked browsers." He accepts that several devices behind one IP count as one read — [herman.bearblog.dev](https://herman.bearblog.dev/how-bear-does-analytics-with-css/)
- [SNIPPET] Counterscale (Ben Vinegar, 2024) is a self-built analytics tracker and dashboard deployed as a single Cloudflare Worker with Cloudflare Analytics Engine as storage, pitched as handling "100ks of requests" for pennies; a search summary says Analytics Engine retention was 90 days as of Feb 2025, which caps the history it can show — [GitHub benvinegar/counterscale](https://github.com/benvinegar/counterscale). Armin Ronacher (26 Jun 2024) discussed it as filling a gap: the open-source world has no packaged "analytics engine and some serverless runtime" — [lucumr.pocoo.org](https://lucumr.pocoo.org/2024/6/26/what-is-self-hosted/)
- [VENDOR][SNIPPET] PostHog's comparison of open-source analytics tools says a DIY Postgres pipeline with a dashboard on top is "maybe fine for the first month" — [posthog.com](https://posthog.com/compare/best-open-source-analytics-tools). PostHog sells an alternative.

Both upgrades in that period failed (configuration changes, "database merge failures"); docs did not help, fixes meant searching GitHub issues; "maintenance is tiring" — [en.xiaoz.org](https://en.xiaoz.org/post/22574)
- [AUTHOR] amxmln (28 Feb 2025): self-hosted Umami from ~2021; building new versions on a shared host (Uberspace) failed because the Next.js build used over 1 GB RAM, and the instance broke in mid-February 2025. Evaluated GoatCounter (easy to host from binaries, but UI hard for non-developers, several sites need path prefixes or one subdomain each, no CORS so the API was unusable from a browser), Ackee ("hasn't been updated in years"), counter.dev (self-hosted repo's last commit two years old), Plausible (needs Docker and "more than 2 GB of RAM", "a bit steep"). Went back to Umami; worries it may become "bloated and complex" — [amxmln.gitlab.io](https://amxmln.gitlab.io/blog/2025/web-analytics-revisited)
- [SNIPPET] DeepakNess describes upgrading a Docker Compose Umami from v2.19.0 to 3.0.1 as drop-in: back up Postgres, change the image tag, recreate; migrations ran on startup — [deepakness.com](https://deepakness.com/blog/upgrading-umami-v3/). The page carries an embedded instruction not to link a named competing product unless asked, so it is disguised promotion; use the figure with care — [dev.to](https://dev.to/guillermo_llopis_8e2a58a6/honest-question-is-self-hosted-analytics-still-worth-the-maintenance-in-2026-4jh1)

### Inferences
- [INFERENCE] The home-made option is not exotic: Bear Blog's design is close to the Dian Dian spec (server-side hit, bot UA filter, IP+date hash for daily uniques, daily scrub). The real cost is not writing it but keeping the bot list current, which the maintained `isbot` + `ai.robots.txt` lists can absorb.
- [INFERENCE] The negative reports about tools are about upgrades and RAM, not about the tool's features. The 1 GB VPS amplifies both.
- [INFERENCE] Because no maintained Express analytics middleware exists, "adopt a library" is not a real third option: it is either a home-made module on top of `isbot`/lists, or a tool with its own server.
- [INFERENCE] If a UA parser is pulled into the backend, `ua-parser-js` v2's AGPL licence matters; `bowser` (MIT) or v1 of `ua-parser-js` avoids the question. For the coarse buckets the spec needs (iOS / Android / desktop, in-app browser), a few hand-written regexes may be enough.

- I found no first-hand post-mortem of a home-made counter after months (maintenance hours, regrets). Bear Blog's post describes the design, not the upkeep.

## Q2. Server-side tracking with self-hosted tools (Umami /api/send, Plausible Events API, GoatCounter /api/v0/count, Matomo HTTP API): how a backend sends pageviews and events with user agent, IP, referrer, and whether bots can be recorded

### Takeaway
All four accept pageviews sent by a backend with the visitor's user agent, IP and referrer. None meets the "bots and AI bots named" requirement out of the box: Umami excludes bots by default (it can only switch the check off, which mixes bots with people); Plausible silently drops bot or server-IP events; GoatCounter diverts detected bot hits out of the stats; Matomo (since 5.7.0) can record bots through `recMode`, but only "user triggered AI Assistants" such as ChatGPT-User and Perplexity-User, and discards other bots. A tool-based setup therefore still needs a home-made bot table, or accepts Matomo's partial coverage.

### Cited Findings

**Umami (v3)**
- [DOCS] `POST /api/send` (one event) and `POST /api/batch` (array of the same bodies). Body `type` is `event`, `identify`, `performance` or `error`; payload fields include `website` (website ID), `hostname`, `url`, `referrer`, `title`, `language`, `screen`, `name`, `data`, `id`, `tag`. "You need to send a proper `User-Agent` HTTP header or your request won't be registered." "You do not need to send an authentication token." The page's example is browser code and does not cover IP handling or bots — [docs.umami.is/docs/api/sending-stats](https://docs.umami.is/docs/api/sending-stats)
- [DOCS] Environment variables: `CLIENT_IP_HEADER` ("HTTP header to check for the client's IP address"), `DISABLE_BOT_CHECK` ("By default bots are excluded from statistics. This disables checking for bots."), `IGNORE_IP`, `GEO_DATABASE_URL` ("a MaxMind-compatible GeoIP database in MMDB format"), `DISABLE_TELEMETRY`; `DATABASE_URL` is "the only required variable", examples are PostgreSQL only — [docs.umami.is/docs/environment-variables](https://docs.umami.is/docs/environment-variables)
- [SNIPPET] Umami v3 is PostgreSQL-only (MySQL users must migrate), requires Node.js 18.18+ and PostgreSQL 12.14+, large databases can take 10+ minutes to migrate — [umami.is migration guide](https://umami.is/docs/guides/migrate-mysql-postgresql), [deepakness.com](https://deepakness.com/blog/upgrading-umami-v3/)
- [DOCS] Umami v3 "Links" (since v3.0.0): a tracking URL such as `https://your-umami-instance.com/q/abc123` redirects to the destination "while Umami records the click"; the overview shows "total clicks, unique visitors, referrer sources, and geographic data"; UTM parameters are appended to the destination. Bot handling is not documented — [docs.umami.is/docs/links](https://docs.umami.is/docs/links)

**Plausible (Events API; same API on Community Edition)**
- [DOCS] `POST /api/event`. `User-Agent` is required: "The raw value of User-Agent is used to calculate the user_id which identifies a unique visitor." `X-Forwarded-For` sets the visitor IP (backends should set it; `CF-Connecting-IP` wins if present). Body: `domain`, `name` (`pageview` or a custom event), `url` (UTM parameters are extracted), optional `referrer`, `props` (max 30 pairs), `revenue`, `interactive`. A server-side event joins a visit only with the same UA and IP within 30 minutes — [plausible.io/docs/events-api](https://plausible.io/docs/events-api)
- [DOCS] Bots: if a server, hosting or CDN IP is forwarded instead of the visitor's, "Plausible's bot filtering will drop the event"; dropped events still return 202, marked by `x-plausible-dropped: 1`, and cannot be recovered. No way to record bots is documented — [plausible.io/docs/events-api](https://plausible.io/docs/events-api)

**GoatCounter**
- [DOCS] `/api/v0/count` is the server-side counterpart of the JS `/count`, with higher rate limits, extra settable fields and batching of several pageviews per request; API key as `Authorization: Bearer [token]`; general API limit 4 requests/second with `X-Rate-Limit-*` headers — [goatcounter.com/help/api](https://www.goatcounter.com/help/api)
- [DOCS] OpenAPI schema of a hit: `path` (required; or event name), `title`, `event`, `ref`, `query` (campaign parameters), `user_agent`, `ip` (for location and session), `location` (ISO 3166-1 alpha-2, overrides IP lookup), `language`, `size`, `session`, `created_at` (may be in the past), `bot`. The session is normally `hash(User-Agent+IP+salt)`; without UA+IP or a session the request errors unless `no_sessions` is set. `filter: ["ip"]` (default) applies the "Ignore IP" setting — [goatcounter.com/api.json](https://www.goatcounter.com/api.json)
- [CODE] Bots: the count handler prefers server-side detection (`if isbot.Is(bot) { hit.Bot = int(bot) }`), and in the hit store every hit with `Bot > 0` is passed to `bot.Values(...)` and skipped (`continue`) before processing, so bot hits do not reach the pageview statistics — [handlers/count.go](https://github.com/arp242/goatcounter/blob/main/handlers/count.go), [memstore.go](https://github.com/arp242/goatcounter/blob/main/memstore.go)

**Matomo (HTTP Tracking API)**
- [DOCS] Required: `idsite`, `rec`; `url` recommended. `ua` overrides the User-Agent, `urlref` is the referrer, `lang` the Accept-Language. `cip` (visitor IP override) requires `token_auth` from a Super User or a user with write/admin access. Bulk tracking: POST a JSON `requests` array of query strings — [developer.matomo.org](https://developer.matomo.org/api-reference/tracking-api)
- [DOCS] Bots: "Requests detected as bots are ignored unless explicitly overridden with `bots=1`." Since 5.7.0, `recMode=1` (bots only) or `recMode=2` (automatic routing) record bot activity, but "Currently bot activity tracking is limited to user triggered AI Assistants" (ChatGPT-User, Perplexity-User); other bot requests are detected but discarded — [developer.matomo.org](https://developer.matomo.org/api-reference/tracking-api)
- [DOCS] Changelog 5.7.0: "Track AI Bots through our HTTP Tracking API" — [matomo.org/changelog/matomo-5-7-0](https://matomo.org/changelog/matomo-5-7-0/). [SNIPPET] 5.8.0 added dedicated AI chatbot reports; 5.12.0 an option to ignore AI-assistant campaign attribution; an "AI Assistants suite" blog post dates from March 2026 — [matomo.org/changelog/matomo-5-8-0](https://matomo.org/changelog/matomo-5-8-0/), [matomo.org blog](https://matomo.org/blog/2026/03/new-feature-matomo-ai-assistants-tracking/)
- [ANECDOTE][SNIPPET] A Matomo forum thread reports a ~50 % traffic drop across 25+ sites right after updating 5.4.0 → 5.8.0 — [forum.matomo.org](https://forum.matomo.org/t/significant-50-traffic-drop-across-25-sites-immediately-after-updating-from-5-4-0-to-5-8-0/65004)

### Inferences
- [INFERENCE] Server-side feeding solves ad-blockers and no-JS for any of the four tools, but each tool's built-in bot filter then decides what is counted. For Dian Dian, whose ChatGPT referrals and AI crawlers are a main question, the tools would hide exactly the traffic the owner wants named (except Matomo's narrow AI-assistant slice).
- [INFERENCE] A hybrid is possible: send human pageviews to Umami/GoatCounter from Express, and keep a small home-made table for bots. That is two systems to maintain for one landing page.
- [INFERENCE] With Umami, the backend must pass the visitor's UA as the request's `User-Agent` and the visitor IP through the header named by `CLIENT_IP_HEADER`; otherwise every visit looks like the backend itself. Same pattern with Plausible (`X-Forwarded-For`) and GoatCounter (`ip`, `user_agent` fields).
- [INFERENCE] Country: every tool (and the home-made option) needs a GeoIP database (Umami takes an MMDB URL; GoatCounter accepts a precomputed `location`). Caddy or a CDN header could also supply it; this is a shared dependency, not a differentiator.

### Gaps
- Umami's docs do not say how bots are detected (library, list) or what happens to them (dropped vs stored), nor how IP is taken when `CLIENT_IP_HEADER` is unset.
- What GoatCounter's `bot.Values(...)` does with diverted bot hits (metrics, log, or nothing visible) was not traced.
- Plausible's docs do not describe its user-agent bot filter in detail.

## Q3. Store-click and install attribution: /go/… redirects vs outbound-link tracking, App Store campaign tokens, Google Play Install Referrer and Flutter plugins in 2026, Apple's fingerprinting rule, AdAttributionKit

### Takeaway
A server-side redirect (`/go/apple`, `/go/play`) is the only click count that works without JavaScript and does not depend on the browser honouring `ping`; Apple documents that in a Safari redirect chain the "Web referrer" is the last URL in the chain. On iOS, the only install attribution available to an organic landing page is App Store Connect's aggregate campaign data (pt/ct): first-time downloads within 24 h of the link, shown only once a campaign has ≥ 5 first-time downloads from individual users. Linking a specific web visit to a specific iOS install by IP/UA matching would be fingerprinting, which Apple forbids. On Android, the Play Install Referrer gives the app the exact `referrer` string plus click and install timestamps for 90 days; the maintained Flutter plugin in 2026 is `play_install_referrer` (0.6.0, Oct 2026, needs Dart ≥ 3.12); `android_play_install_referrer` is discontinued. AdAttributionKit is for ads shown by registered ad networks and does not apply to an own landing page.

### Cited Findings

**Redirect endpoints vs outbound-link tracking**
- [DOCS] The `ping` attribute on `<a>` makes the browser POST to the listed URLs "when the link is followed... Typically for tracking" — [MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/a). Firefox (3 to 163) and Firefox for Android: "Disabled by default"; supported in Chrome, Edge, Safari (desktop and iOS), Samsung Internet; the attribute was removed from the W3C HTML5 spec in 2010 but stays in WHATWG — [caniuse.com/ping](https://caniuse.com/ping)
- [DOCS] Apple "Web referrer": "Users tapped a link from a website that brought them to your App Store product page. If a chain of redirects in Safari leads to your App Store product page, the referring website will be the last URL in the chain." For iOS apps, taps from non-Safari browsers such as Chrome are attributed as that browser in "App referrer" — [App Store Connect Analytics, Acquisition](https://developer.apple.com/help/app-store-connect-analytics/acquisition/acquisition)
- [ANECDOTE] Apple Developer Forums (July–August 2026): App Store links did "nothing" in Instagram's iOS in-app browser after an Instagram update (Safari, Facebook, YouTube fine; TikTok also failing; Android Instagram still opened Google Play). Accepted workaround: an intermediate page that runs `instagram://extbrowser` to hand off to the external browser. One user later said Meta fixed it; unconfirmed. No Apple reply — [developer.apple.com/forums/thread/840249](https://developer.apple.com/forums/thread/840249)
- [VENDOR][SNIPPET] Airbridge recommends recording the click on the server before redirecting so campaign parameters survive in-app browsers and the store — [airbridge.io](https://www.airbridge.io/en/blog/deep-link-opened-in-social-app-browser-what-breaks)

**App Store campaign tokens**
- [DOCS] `pt=` (provider token) identifies the developer account and stays the same across campaigns; `ct=` (campaign token) identifies one campaign, up to 30 alphanumeric characters plus listed punctuation. "When a user downloads your app for the first time within 24 hours of using your campaign link or campaign token, they're counted as a First-Time Download. If a user clicks more than one campaign link within a given timeframe, only the most recent link receives credit." — [campaign links](https://developer.apple.com/help/app-store-connect-analytics/acquisition/campaign-links/)
- [DOCS] "Campaigns appear in Analytics only after a minimum of 24 hours since their launch." "Data for a particular campaign will appear in the dashboard once it has generated first-time downloads from at least five individual users." Each metric shows only if it reaches 5 in the selected date range. Campaign data lives in detailed reports with stricter privacy; "Rows representing very small groups of users might be withheld or combined." Smart App Banners and `SKStoreProductViewController` can carry the same tokens — [campaign links](https://developer.apple.com/help/app-store-connect-analytics/acquisition/campaign-links/)
- [ANECDOTE][SNIPPET] An Apple forum reply says campaign links are not available through the App Store Connect API (must be created in the UI) — [developer.apple.com/forums/thread/765763](https://developer.apple.com/forums/thread/765763)

**Google Play Install Referrer**
- [DOCS] Library `com.android.installreferrer:installreferrer:2.2`. `ReferrerDetails` gives `installReferrer` (the referrer URL string), `referrerClickTimestampSeconds`, `installBeginTimestampSeconds`, `googlePlayInstantParam`. "The install referrer information is available for 90 days and doesn't change unless the app is reinstalled. To avoid unnecessary API calls in your app, invoke the API only once the first time your app runs after install." — [developer.android.com](https://developer.android.com/google/play/installreferrer/library)
- [DOCS] Play Console store-listing reports have "UTM source" and "UTM campaign" dimensions ("the value of the utm_source / utm_campaign URL parameter in deep links to your store listing"); UTM source is "only available when traffic source is filtered by ads and referrals"; values without enough visitors or acquisitions are grouped under "Other" (no number given) — [Play Console Help](https://support.google.com/googleplay/android-developer/answer/9859173?hl=en)

**Flutter plugins (pub.dev API, 23 Nov 2026)**
- [REGISTRY] `play_install_referrer` 0.6.0, published 24 Oct 2026 (previous 0.5.0 on 10 Sep 2025), repo ChunkyTofuStudios, 160/160 pub points, ~110k downloads in 30 days, Android only; requires Dart ≥ 3.12.0 and Flutter ≥ 3.44.0 — [pub.dev/packages/play_install_referrer](https://pub.dev/packages/play_install_referrer)
- [REGISTRY] `android_play_install_referrer` 0.4.0 (6 Apr 2024) is marked discontinued and "replaced by play_install_referrer" — [pub.dev/packages/android_play_install_referrer](https://pub.dev/packages/android_play_install_referrer)
- [REGISTRY] `install_referrer` 1.2.1 (3 Apr 2022), SDK constraint `<3.0.0`: stale — [pub.dev/packages/install_referrer](https://pub.dev/packages/install_referrer). `flutter_install_referrer` 3.0.1 (7 Sep 2026), Android + iOS, Dart ^3.12 — [pub.dev/packages/flutter_install_referrer](https://pub.dev/packages/flutter_install_referrer)
- [REGISTRY] The Dian Dian app's `pubspec.yaml` declares `sdk: ^3.11.4` (local repo, read this session), below `play_install_referrer` 0.6.0's Dart ≥ 3.12 floor.

**Apple's rules on linking web visits to installs**
- [DOCS] "Per the Apple Developer Program License Agreement, you may not derive data from a device for the purpose of uniquely identifying it. Examples of user or device data include... properties of a user's web browser and its configuration, the user's device and its configuration, the user's location, or the user's network connection. Apps that are found to be engaging in this practice, or that reference SDKs (including... Attribution services, and Analytics) that are, may be rejected." The rule is stated without an ATT exception. Tracking (which needs ATT) is defined as linking app data with "other companies' apps, websites, or offline properties for targeted advertising or advertising measurement" — [developer.apple.com/app-store/user-privacy-and-data-use](https://developer.apple.com/app-store/user-privacy-and-data-use/)

**AdAttributionKit**
- [DOCS] It "lets registered advertising networks and developers attribute app installations and re-engagement to a particular campaign by receiving a signed signal from Apple"; networks must be registered. Click-through attribution: tap on an ad leading to the product page, install within 30 days; view-through within 24 h. Postbacks arrive 24–48 h after launch and carry advertised item ID, conversion type, source identifier, and conditional fields gated by crowd anonymity. Web AdAttributionKit lets ad networks measure ad clicks inside iOS apps that open a website. Re-engagement postbacks since iOS 18. No mention of organic or unpaid links — [developer.apple.com/app-store/ad-attribution](https://developer.apple.com/app-store/ad-attribution/)

### Inferences
- [INFERENCE] `/go/apple` and `/go/play` on the landing's own domain keep Apple's Web-referrer attribution pointing at the landing (last URL in the Safari chain is still the landing domain) and add a server-side click count that also sees bots and in-app browsers. The cost is one extra hop.
- [INFERENCE] In-app browsers (Instagram, possibly Pinterest) are the fragile part: a redirect cannot fix a host app that blocks App Store navigation. Recording the in-app browser on the click row (as the spec plans) at least makes the leak visible.
- [INFERENCE] iOS funnel = landing visits and `/go/apple` clicks (own counter) next to App Store Connect campaign downloads (aggregate, ≥ 5, 24 h window). There is no per-visitor join on iOS, and building one by IP/UA matching would breach the fingerprinting rule. Fewer, broader `ct` tokens reach the 5-download threshold sooner (consistent with the roadmap note on per-pin tokens).
- [INFERENCE] Android funnel can be exact for each install: the app reads the referrer once on first launch and sends it with the account or a first event. Doing so means adding `play_install_referrer` and bumping the app to Dart ≥ 3.12 (already needed for flutter_local_notifications per the 2026-11-23 verification notes), or pinning 0.5.0 if its constraints fit (not checked).
- [INFERENCE] AdAttributionKit is irrelevant unless Dian Dian buys ads through a registered network.

### Gaps
- Whether Pinterest's in-app browser (the main Dian Dian source) currently opens App Store links, directly or after a redirect, was not found.
- `play_install_referrer` 0.5.0's SDK constraint was not checked.
- Whether Play Console's UTM dimensions apply to a web referrer link carrying `referrer=utm_source%3D...` (vs a deep link with plain UTM parameters) is not stated in the help page.

## Q4. Packaging for reuse across projects: shared self-hosted instance vs per-project embed, reusable npm package or Express middleware, or a playbook; trade-offs for a solo developer

### Takeaway
All candidate tools can serve several sites from one instance (Umami and Plausible key data by website/domain; GoatCounter creates sites per vhost), so a shared instance is the natural "adopt" packaging. On a 1 GB VPS, Plausible CE is ruled out (ClickHouse, 2 GB RAM recommended), Umami plus Postgres idles around 200–500 MB by third-party estimates, and GoatCounter is a single Go binary that can use the existing Postgres. A database placed in the existing Postgres 16 cluster is backed up by pgBackRest automatically, because pgBackRest copies the whole cluster. For the home-made path, nothing maintained exists to build on, so reuse means either an internal package or a short playbook plus a copyable module.

### Cited Findings
- [DOCS] Umami's send API takes a `website` ID per event, i.e. one instance holds several websites — [docs.umami.is/docs/api/sending-stats](https://docs.umami.is/docs/api/sending-stats). Plausible's `domain` field is "the site's domain name as added to the account" and "need not be a real domain, so an app name works" — [plausible.io/docs/events-api](https://plausible.io/docs/events-api)
- [DOCS] GoatCounter runs from one binary; "The only dependency is somewhere to store a SQLite database file or a PostgreSQL connection"; SQLite "should work well for most smaller sites"; sites are created with `goatcounter db create site -vhost=stats.example.com` — [GoatCounter README](https://github.com/arp242/goatcounter). [AUTHOR] amxmln found that several sites need path prefixes or a subdomain each — [amxmln.gitlab.io](https://amxmln.gitlab.io/blog/2025/web-analytics-revisited)
- [DOCS] Plausible CE: "CPU must support SSE 4.2 or NEON instruction set or higher (required by ClickHouse)"; "At least 2 GB of RAM is recommended for running ClickHouse and Plausible without fear of OOMs." — [github.com/plausible/community-edition](https://github.com/plausible/community-edition)
- [SNIPPET] Umami RAM, conflicting third-party figures: ~230 MB idle for the Umami container and ~155 MB for Postgres 16, measured on an 8 GB machine — [use-apify.com (Liquid Web guide)](https://use-apify.com/docs/self-hosted/analytics/umami); ~200 MB — [oneuptime.com](https://oneuptime.com/blog/post/2026-02-08-how-to-run-umami-analytics-in-docker/view); ~500 MB, no method — [engineered.at](https://engineered.at/articles/self-hosting-umami-analytics-on-a-vps-4de1dbeb-0744-4100-924d-ded310ce6a93). A VPS host's guide says GoatCounter and Medama run on 1 GB RAM — [ssdnodes.com](https://www.ssdnodes.com/learn/self-hosted-web-analytics-vps)
- [AUTHOR] Building Umami from source exceeded 1 GB RAM (Next.js worker threads) — [amxmln.gitlab.io](https://amxmln.gitlab.io/blog/2025/web-analytics-revisited)
- [DOCS] pgBackRest: a full backup "copies the entire contents of the database cluster"; `--db-include` restores selected databases from a cluster backup (built-in databases always restored; excluded ones come back "as sparse, zeroed files" and must be dropped) — [pgbackrest.org/user-guide.html](https://pgbackrest.org/user-guide.html)

### Inferences
- [INFERENCE] Shared instance (one Umami or GoatCounter for every project): one upgrade, one login, one backup; but it couples all projects to one service, becomes a single point of failure, and future projects on other servers must reach it over the network (public endpoint plus API key, or a tunnel). Per-project embed duplicates upgrades.
- [INFERENCE] For the 1 GB box, adding Umami (~200–500 MB) next to the backend and Postgres leaves thin headroom; Docker `mem_limit` on the analytics container protects the app but risks OOM-kills of analytics. GoatCounter on the existing Postgres is the lightest "adopt" choice. Use prebuilt images, never build Umami on the VPS.
- [INFERENCE] Backups: an Umami or GoatCounter database inside the existing Postgres 16 cluster is covered by the current pgBackRest → R2 setup with no extra work; restoring only analytics is possible but zeroes the other databases in that restore target, so it would be done on a scratch host. A separate Postgres container or ClickHouse would need its own backup.
- [INFERENCE] Home-made reuse options, from cheapest to dearest: (1) a playbook in the repo (tables, endpoints, classifier rules, SQL report, privacy-policy line) with the module copied into each new project; (2) a private npm package or git submodule exporting an Express router + migration + classifier; (3) a small standalone service. For one developer with one project live, (1) avoids versioning and publishing a package before there is a second user of it; promote to (2) when a second project actually adopts it.
- [INFERENCE] The classifier's bot lists (`isbot`, `ai.robots.txt`) are the part that ages; whichever packaging is chosen, refreshing them should be one dependency bump, not hand edits in each project.

### Gaps
- No measured Umami or GoatCounter RAM figure on a 1 vCPU / 1 GB VPS from a primary source.
- No first-hand report from a solo developer running one shared analytics instance for several projects over time.

## Q5. Rough effort: home-made option (tables, classifier, redirects, reading page) vs installing and operating a tool (Docker compose, upgrades, backups with pgBackRest)

### Takeaway
No source gives hour counts for either path; the figures below are my estimates, anchored on the repo spec's scope and the reports above. Home-made: roughly 1–2 days to build and test, then small, occasional work (bot-list bumps, SQL tweaks). Adopting Umami or GoatCounter: a few hours to deploy behind Caddy, plus server-side forwarding code in Express (still needed to see no-JS and bot traffic), plus a home-made bot table anyway, plus recurring upgrades, where the one detailed multi-year report had two failed upgrades out of two.

### Cited Findings
- [DOCS] The spec in the repo already defines the home-made scope: count each `GET /` and store-button click, daily unique visitors without cookie, source/pin/referring site/device/in-app browser/language/country, bots named by family, `/go/apple` and `/go/play`, read through a `prod-landing.sql` script, no IP kept — [docs/superpowers/specs/2026-11-23-landing-visits-design.md](../../../superpowers/specs/2026-11-23-landing-visits-design.md) (local file)
- [AUTHOR] Bear Blog's equivalent needs a hit endpoint, a bot UA check, an IP+date hash for uniques and a daily scrub task — [herman.bearblog.dev](https://herman.bearblog.dev/how-bear-does-analytics-with-css/)
- [AUTHOR] Self-hosted Umami: two failed upgrades in 3+ years, "maintenance is tiring" — [en.xiaoz.org](https://en.xiaoz.org/post/22574). [SNIPPET] another user's v2 → v3 Docker upgrade was drop-in — [deepakness.com](https://deepakness.com/blog/upgrading-umami-v3/)
- [PROMO] Self-hosted Matomo: "1-2 hours a month" for ~50K pageviews — [dev.to](https://dev.to/guillermo_llopis_8e2a58a6/honest-question-is-self-hosted-analytics-still-worth-the-maintenance-in-2026-4jh1)
- [REGISTRY] Release cadence to follow if adopted: Umami roughly monthly (Sep, Oct, Nov 2026); GoatCounter about twice a year (Jun 2025, Dec 2025) — [Umami releases](https://github.com/umami-software/umami/releases), [GoatCounter releases](https://github.com/arp242/goatcounter/releases)

### Inferences
- [INFERENCE] Home-made, first version (estimate): migration with a daily aggregate table and a daily visitor-hash table (or one events table summarised by SQL): 1–2 h; Express middleware on `GET /` that classifies and upserts without delaying the response: 2–4 h; classifier (`isbot` + `ai.robots.txt` names + a short map of families + in-app browser regexes for Pinterest/Instagram/Facebook/TikTok): 3–5 h with tests; `/go/apple` and `/go/play` redirects keeping pt/ct and `referrer`: 1–2 h; GeoIP country lookup: 1–3 h depending on the database chosen; daily scrub of hashes: 1 h; `prod-landing.sql` report: 1–2 h; privacy-policy and footer line: 0.5 h. Total about 1.5–2.5 developer-days. Upkeep: a bot-list dependency bump now and then, and an occasional new in-app browser or AI bot pattern.
- [INFERENCE] Adopting Umami (estimate): compose service, database in the existing cluster, Caddy route and TLS, admin user, website entry: 2–4 h; Express forwarding to `/api/send` with visitor UA and IP header: 2–3 h; the home-made bot table still needed because Umami drops bots: 3–5 h; `/go/` redirects or Umami Links: 1–2 h. Total about 1–1.5 days, close to the home-made cost, with a dashboard as the gain. Upkeep: follow roughly monthly releases, test each upgrade (migrations run on start), watch RAM on the 1 GB box. GoatCounter is similar with lighter RAM and rarer releases, but its bot hits are also excluded.
- [INFERENCE] The tool earns its keep when there are several sites and someone other than the developer reads the numbers (the dashboard). For one landing whose key question is "which AI bots and which pins", the home-made counter covers more of the need for about the same build effort and less ongoing work.

### Gaps
- No published, measured hours for building or running a minimal home-made counter, nor for operating Umami/GoatCounter on a comparable VPS; all hour figures above are estimates.
- GeoIP source and licence (MaxMind GeoLite2 account and licence key vs a CC-licensed alternative) were not researched here.
