# Android mechanisms for carrying a small app secret and local data to a new phone, or across uninstall and reinstall, without an account (state at 2026-11-26)

Context: an iOS + Android Flutter app creates, on first launch, a random 32-byte "device key" that opens an identity-less space on the server. A full copy of the data also stays on the phone. Today the key would sit only in Keystore-encrypted storage, as flutter_secure_storage does on Android. The manifest has no `allowBackup`, `fullBackupContent` or `dataExtractionRules`, so platform defaults apply. The goal is for the key, and ideally the data, to follow the person to a new Android phone, and for settings to show a truthful status. These notes cover only the Android platform side: Block Store, Restore Credentials, Auto Backup and device-to-device (D2D) transfer, the Keystore restore failure, what an app can detect, and whether anything syncs a secret live between two phones in use. They build on the Auto Backup bullets in `docs/research/notes/Utiliser l'app sans compte/apps_comparables_risques.md`, re-verified below. Every source was read on 2026-11-26. Most developer.android.com pages did not show a "last updated" date in the fetched copy; dates are given where shown.

Evidence labels:
- [PRIMARY] the platform owner's own documentation (developer.android.com, developers.google.com, Google support, Android Developers Blog, Google Maven, Play Console Help).
- [DOCS] package documentation.
- [ISSUE] a bug report or developer account, with its text quoted. A Google staff reply on an issue tracker is marked as such.
- [VENDOR] a company describing its own product.
- [COMMENTARY] third-party blogs or articles.
- [SEARCH] known only from a search snippet; the page was not read.
- [INFERENCE] my own reasoning, naming the sources it rests on.

## Q8a. Block Store (com.google.android.gms.auth.blockstore): status, limits, cloud backup, E2EE, restore, uninstall, devices without Play services

### Takeaway
Block Store still works and is still documented. It has not been formally deprecated, but Google now points people elsewhere. The page opens by recommending passkeys with Credential Manager, the backup overview names Restore Credentials as "the recommended way", and the library has had no release since 16.4.0 in July 2024. Block Store stores up to 16 byte arrays, each identified by a key, inside Google Play services. A 32-byte device key fits easily. The data always stays on the device. It goes to the cloud only if the app sets `setShouldBackupToCloud(true)`, and that backup is end-to-end encrypted only on Android 9+ with a screen lock. It moves to a new phone only through a restore flow that also transfers the Google Account (D2D or cloud restore). The app can read it at any later time with `retrieveBytes()`. If the user has Google backup on, Block Store data survives an uninstall and reinstall on the same device. That is something Restore Credentials does not do. Block Store needs Google Play services, and for sign-in purposes Play only accepts it if it was in production by 30 Sep 2026 (see Q8d).

### Cited Findings
- [PRIMARY] The Block Store page now opens with: "**Important:** For an updated user experience and other improvements, consider using Passkeys with Credential Manager instead." It describes Block Store as "a library powered by Google Play services" that "allows your app to store data that it can later retrieve to re-authenticate users on a new device." — https://developer.android.com/identity/block-store, read 2026-11-26
- [PRIMARY] Latest artifact: Google Maven metadata for `com.google.android.gms:play-services-auth-blockstore` gives `<latest>16.4.0</latest>`, `lastUpdated 20240725184704`. The 16.4.0 POM is `last-modified: Thu, 25 Jul 2024`, so there has been no release in more than two years. The docs page still shows `play-services-auth-blockstore:16.4.0`. — https://dl.google.com/android/maven2/com/google/android/gms/play-services-auth-blockstore/maven-metadata.xml, read 2026-11-26
- [PRIMARY] Capacity: "Block Store allows developers to save and restore up to 16 byte arrays" and "a unique key pair value that has a maximum 4kb per entry". — https://developer.android.com/identity/block-store. **Conflict:** the API reference gives `MAX_SIZE` = 1024: "The maximum size of String key and byte[] bytes combined is MAX_SIZE". It also gives `MAX_ENTRY_COUNT` = 16: "Maximum number of distinct data entries, differentiated by the data keys". Errors are `MAX_SIZE_EXCEEDED` and `TOO_MANY_ENTRIES`. — https://developers.google.com/android/reference/com/google/android/gms/auth/blockstore/BlockstoreClient, read 2026-11-26. Either way a 32-byte key fits.
- [PRIMARY] Storage location and isolation: "On device, Block Store data is stored in Google Play services' local private data directory… an app can only retrieve data stored by itself. Google Play services checks both the package name and signature." Writes overwrite: "Successive calls with the same key to this API will overwrite the existing bytes." — block-store page and BlockstoreClient reference, read 2026-11-26
- [PRIMARY] Flow: "The token will be stored locally and can also be backed up to the cloud, end-to-end encrypted when possible. Data is transferred when the user initiates a restore flow on a new device." Also: "The user has already agreed to restore your app data as a part of the restore flow, so no additional consents are required." — https://developer.android.com/identity/block-store, read 2026-11-26
- [PRIMARY] D2D needs the Google Account to move: storeBytes data "is transferred to a new device during the device-to-device restore" if a Google account is also transferred (reference). The testing page adds: "Block Store only works for restore flows that include Google's account transfer functionality, since this is how we verify the user's identity… If the Google Account is not transferred, neither will the Block Store data." For Samsung Smart Switch, "Accounts" must be selected. Smart Switch can also run outside setup. — https://developer.android.com/identity/block-store/testing-restore-flows, read 2026-11-26
- [PRIMARY] Cloud backup: "Block Store will periodically backup to cloud the bytes stored when `setShouldBackupToCloud()` is set as true." Google recommends turning it on "only when cloud backup is end-to-end encrypted" and otherwise to "only store bytes for D2D restore". If storeBytes is later called with the flag unset or false, "this device's bytes previously backed up to cloud will be deleted from the cloud upon next periodic sync." — block-store page, read 2026-11-26
- [PRIMARY] E2EE conditions: "the device must be running Android 9 or higher, and the user must have set a screen lock (PIN, pattern, or password)". `isEndToEndEncryptionAvailable()` "will return false if any of these conditions is not met." The reference says: "End-to-end encryption is available for Pie and above devices with a lockscreen PIN/pattern." — block-store page and BlockstoreClient reference. (The page's "Device Requirements" section writes "Android 9 (API 29)", but Android 9 is API 28, so that is a documentation slip.)
- [PRIMARY] Device requirements: D2D source Android 6+ and target "Android 9 (API 29) or later". For cloud restore: "Pixel devices can use this feature from Android 9 (API 29) and all other devices must be running Android 12 (API 31) or later." — https://developer.android.com/identity/block-store, read 2026-11-26
- [PRIMARY] Reading later: `retrieveBytes` "data may have been written on the same device or may have been transferred during the device setup. If no data is found, returns an empty data map." Caveat: "the data may be cleared by Google Play services on certain user actions". The reference does not list those actions. — BlockstoreClient reference, read 2026-11-26
- [PRIMARY] Same device, uninstall then reinstall: "If the user enables Backup services (it can be checked at **Settings > Google > Backup**), Block Store data is persisted across an app uninstall and reinstall." — block-store page, "How to test", read 2026-11-26
- [PRIMARY] Auto Backup's own docs still say: "To back up user credentials and authentication tokens, don't store them in shared preferences or a file. Instead use Block Store APIs". — https://developer.android.com/identity/data/autobackup, read 2026-11-26. This conflicts with the newer guidance (Q8d).
- [PRIMARY] Play's zero-tap rule: Block Store integrations "may be considered compliant but only if the integration was completed and in production on or before September 30, 2026". — https://support.google.com/googleplay/android-developer/answer/17492799, read 2026-11-26

### Inferences
- [INFERENCE] With backup off, the cloud path is gone and same-device persistence after uninstall is not promised (the only documented condition is "If the user enables Backup services"). D2D transfer should still carry Block Store data, because it travels with the Google Account transfer, not with cloud backup. Google does not state this for backup-off. Sources: block-store page, testing-restore-flows.
- [INFERENCE] Block Store does nothing on devices without Google Play services (Huawei/HMS, de-Googled ROMs). It is "powered by Google Play services" and identity is verified through Google Account transfer. I found no explicit statement of the error the API returns there.
- [INFERENCE] Of all the Android mechanisms, Block Store is the only one that can carry the existing 32-byte device key as-is, with no server change. Restore Credentials needs a WebAuthn server (Q8b). For an account-less app the Play compliance cutoff does not matter (see Q8d), but the "consider passkeys instead" banner and two years without a release mean Block Store should be treated as legacy that still works, not as a growing API.

## Q8b. Restore Credentials (Credential Manager "restore key")

### Takeaway
A restore key is a passkey-like WebAuthn key pair that Google Play services creates silently for the app and carries to a new phone during setup. It travels by end-to-end encrypted cloud backup or by cable or Wi-Fi D2D, whatever the app's `allowBackup` setting. It needs a WebAuthn relying-party server: a registration ceremony when the key is created, and an unauthenticated, userless assertion on the new phone, from which the server finds the account via `userHandle`. Minimums are Android 9 (API 28), Play services 242200000 (v24.22) and `androidx.credentials` 1.5.0. Today the latest is 1.7.0-alpha03 and the latest stable is 1.6.0. Cloud backup of the key requires a Google Account, backup turned on and a screen lock. Otherwise `E2eeUnavailableException` is thrown and the app should fall back to a local-only key, which D2D still carries. The user sees no UI, either when the key is created or when it is used on the new phone. The key is deleted on uninstall or clear-data, so unlike Block Store it does not help a reinstall on the same phone. There is one restore key per app (one account).

### Cited Findings
- [PRIMARY] Definition: "A restore credential, also known as a restore key, is a type of credential that can be saved locally or backed up to a cloud provider, and then used to provision access on the user's new device." Google adds: "It is a particularly recommended feature for apps that already support passkeys because of the common underlying server-side implementation." — https://developer.android.com/identity/sign-in/restore-credentials, read 2026-11-26
- [PRIMARY] Server: "Configure a WebAuthn relying party server similar to the server for passkeys… you can reuse the same WebAuthn registration and assertion endpoints for restore keys." Also: "your client-side app can support restore keys without supporting user-facing passkeys. Store restore keys with a distinct credential flag in your backend database". — https://developer.android.com/identity/sign-in/restore-credentials-implementation, read 2026-11-26
- [PRIMARY] Creation JSON follows passkey registration: `challenge`, `rp {name, id}`, `user {id, name, displayName}`, `pubKeyCredParams`, `"attestation": "none"`, `residentKey: required`. `challenge` and `user.id` must be unpadded Base64URL: "Standard Base64 characters or raw integer IDs cause `CreateRestoreCredentialDomException` or `IllegalArgumentException`." `rp.id` is "your relying party's domain". The response's `registrationResponseJson` goes to the server "to verify and store the public key alongside the user's account". — implementation page, read 2026-11-26
- [PRIMARY] New phone: the options endpoint "must be **unauthenticated** (userless discovery)", with `allowCredentials` empty. The server identifies the user "from the `response.userHandle` field (which matches the `user.id` registered during creation)". "Because Restore Credentials runs silently without biometric or screen-lock UI, Android overrides `"required"` to `"discouraged"`, and the authenticator data… has the User Verified (`uv`) flag set to `false`." — implementation page, read 2026-11-26
- [PRIMARY] Versions: "works on devices running Android 9 (API level 28) and higher, Google Play services (GMS) core version `242200000` (v24.22) or higher, and version `1.5.0` or higher of the `androidx.credentials` library. On devices without Google Play services or with an older GMS version, catch `CreateCredentialProviderConfigurationException` and `GetCredentialProviderConfigurationException` so your app falls back gracefully". The page shows `credentials:1.7.0-alpha03`. — implementation page. Google Maven lists `1.6.0` as the latest stable and `1.7.0-alpha03` as latest. — https://dl.google.com/android/maven2/androidx/credentials/credentials/maven-metadata.xml, read 2026-11-26
- [PRIMARY] Scope: it works on "Android phones, foldables, and tablets running Android 9 (API level 28) or higher… Cross-device-category restoration… isn't supported". It "supports only one account per app". — https://developer.android.com/identity/sign-in/restore-credentials. "A restore key is tied to an application's unique package name." — implementation page
- [PRIMARY] Cloud conditions: the user must "Be signed in to their Google Account", "Have Android data backup enabled" and "Have a screen unlock mechanism set up… If these conditions aren't met, an `E2eeUnavailableException` is thrown." The app should then call again with `isCloudBackupEnabled = false` "so the restore key is still saved locally for device-to-device (D2D) transfers." — overview page. With false, "The key is not available on the new device if the user chooses to restore from the cloud, but it still transfers during a local cable or Wi-Fi device-to-device (D2D) setup." — implementation page, read 2026-11-26
- [PRIMARY] Independence from allowBackup: "Google Play services transfers the `RestoreCredential` key pair using end-to-end encrypted cloud backup or local device-to-device (D2D) transfer regardless of whether `android:allowBackup` is `true` or `false`. For D2D transfers, the restore key always transfers; the only condition under which it isn't transferred is during a cloud backup when the user has opted out of cloud backup in Android Settings." — implementation page, read 2026-11-26
- [PRIMARY] No UI: "The process of generating the restore key is silent and doesn't require user interaction after their initial authentication." On the new phone, "Restore Credentials works silently in the background during the device setup process". — overview page, read 2026-11-26
- [PRIMARY] Restore happens only at new-device setup, from a cloud backup or by D2D. Retrieval works in two tiers: `BackupAgent.onRestoreFinished()`, which needs `allowBackup="true"` and a `backupAgent`, then a fallback in the launcher Activity on first launch. `getCredential` throws `NoCredentialException` when "No restore key is present on this device". — overview and implementation pages, read 2026-11-26
- [PRIMARY] Uninstall: "Uninstalling an app or clearing app data deletes the local restore key without notifying your server." Keys are removed only by "System-level actions: Users uninstall the app or clear its data" or by `clearCredentialState(ClearCredentialStateRequest(TYPE_CLEAR_RESTORE_CREDENTIAL))`. — implementation page. Play's FAQ: "No. The restore key is automatically deleted when an app is uninstalled." — https://support.google.com/googleplay/android-developer/answer/17492799, read 2026-11-26
- [PRIMARY] Marker caution: the local `has_synced_restore_credential` flag must not live in backed-up prefs "otherwise, Auto Backup copies `has_synced_restore_credential = true` onto the new device and prevents the new device from generating or rotating its own restore key." — implementation page, read 2026-11-26
- [PRIMARY] History: the feature was introduced on 20 Nov 2024 (Android Developers Blog, Neelansh Sahai). It "Leverages the same server-side implementation used for passkeys" and is "a public key compatible with passkey / FIDO2 backends". The initial minimum was `1.5.0-beta01`. The post does not mention Block Store. — https://android-developers.googleblog.com/2024/11/maintain-strong-user-relationships-with-restore-credentials.html, read 2026-11-26
- [ISSUE] Digital Asset Links: the docs I read do not say whether `assetlinks.json` is required for restore keys. Passkeys do require it ("Digital Asset Links are required for passkeys" — https://developer.android.com/identity/passwords). Developer reports conflict. One GitHub issue plans to "Serve Android Digital Asset Links (assetlinks.json)… for Restore Credentials" (https://github.com/bpronin90/kilo/issues/1164). A search snippet claims no DAL check applies to restore keys [SEARCH]. Unresolved.

### Inferences
- [INFERENCE] For an account-less design, the restore key cannot hold the 32-byte device key itself: the key pair is generated by Play services. It can still stand in for it. Put the space's opaque ID, Base64URL-encoded, in `user.id`; keep the public key server-side next to that space; on the new phone, verify the userless assertion and hand back the device key or a new one. This means adding WebAuthn registration and verification to the server, with `rp.id` set to a domain the team controls (sources: implementation page). The `user.name` and `displayName` fields are required in the JSON but are never shown to the user, because there is no UI.
- [INFERENCE] Restore Credentials covers "new phone set up from the old one" but not "uninstalled to fix a bug". Block Store, with backup on, or Auto Backup cover that second case (sources: Play FAQ, block-store page).

## Q8c. Auto Backup for Apps and device-to-device transfer

### Takeaway
Re-verified: Auto Backup is on by default for apps targeting API 23+. With no manifest attributes it backs up shared prefs, `getFilesDir()`, databases and `getExternalFilesDir()`. It skips cache, code_cache and `no_backup`. The backup goes to a private Drive area capped at 25 MB per app, end-to-end encrypted on Android 9+ with a screen lock. It runs only when backup is on, at least 24 h after the last backup, while the device is idle and on Wi-Fi, so "a device might never back up". Restore happens at install time, from the device's own dataset or from the "ancestral" dataset picked in the setup wizard. With no `dataExtractionRules`, D2D transfer on Android 12+ copies everything except no_backup and cache. For apps targeting 31+, `allowBackup="false"` does not stop D2D on some manufacturers' devices. Since Android 16 QPR2, `<cross-platform-transfer platform="ios">` lets an app opt in to iPhone-to-Android transfers. Google's Android 17 "upgraded" switch flow moves third-party app data only "at app developer's discretion". The classic Switch to Android flow moved no third-party app data.

### Cited Findings
- [PRIMARY] Scope and encryption: Auto Backup "automatically backs up a user's data from apps that target and run on Android 6.0 (API level 23) or higher… The backup is end-to-end encrypted on devices running Android 9 or higher using the device's PIN, pattern, or password. Every app can allocate up to 25 MB of backup data per app user." — https://developer.android.com/identity/data/autobackup, read 2026-11-26
- [PRIMARY] Default contents: "Shared preferences files", `getFilesDir()`/`getDir()`, `getDatabasePath()`, and `getExternalFilesDir()`. "Auto Backup excludes files in directories returned by `getCacheDir()`, `getCodeCacheDir()`, and `getNoBackupFilesDir()`." — autobackup page
- [PRIMARY] Over 25 MB: "the system calls `onQuotaExceeded()` and doesn't back up data to the cloud. The system periodically checks whether the amount of data later falls under the 25 MB threshold and continues Auto Backup when it does." Also: "Only the most recent backup is stored." "Backups from each device-setup-lifetime are stored in separate datasets… Obsolete datasets are automatically deleted after a period of inactivity." — autobackup page
- [PRIMARY] Schedule: backups need all of "The user has enabled backup on the device", "At least 24 hours have elapsed since the last backup", "The device is idle", and Wi-Fi "if the device user hasn't opted in to mobile-data backups". "In practice, these conditions occur roughly every night, but a device might never back up". During a backup "the system shuts down the app" and by default skips foreground apps (`android:backupInForeground`). — autobackup page
- [PRIMARY] Restore: "Data is restored whenever the app is installed, whether from the Play Store, during device setup… or by running `adb` install. The restore operation occurs after the APK is installed but before the app is available to be launched by the user." "If the user didn't go through the device setup wizard, then the device can restore only from its own backups." — autobackup page
- [PRIMARY] Account: key-value and Auto Backup both need no sign-in to the app, but "The user must be logged into the device with a Google Account". Auto Backup is recommended "because it's enabled by default and requires no work to implement". — https://developer.android.com/guide/topics/data/backup, read 2026-11-26
- [PRIMARY] allowBackup: "The default value is `true`". "For apps targeting Android 12 (API level 31) or higher… On devices from some device manufacturers, specifying `android:allowBackup="false"` disables cloud-based backup and restore… but doesn't disable device-to-device transfers for the app." — autobackup page; also https://developer.android.com/about/versions/12/behavior-changes-12 ("Backup and restore"), read 2026-11-26
- [PRIMARY] Rules by Android version: `fullBackupContent` applies on Android 11 and lower, and also on 12+ when the app targets 11 or lower. `dataExtractionRules` applies on 12+ for apps targeting 31+, which "must also specify another set of XML backup rules" for ≤11. On Android 12+, the old XML rules "doesn't affect D2D transfers". "If there are no rules for a particular backup mode, such as if the `<device-transfer>` section is missing, that mode is fully enabled for all content except for `no-backup` and `cache` directories". — autobackup page and Android 12 behaviour-changes page
- [PRIMARY] Encryption gate: `disableIfNoEncryptionCapabilities` in `<cloud-backup>` "stops backups from being sent to the cloud if the user's device cannot support encryption, but because D2D transfers aren't sent to the server, they continue to operate even on devices that don't support encryption." On ≤11 the equivalent is `requireFlags="clientSideEncryption"`, which is "enabled on devices running Android 9 or higher as long as the user has enabled backup… and has set a screen lock". — autobackup page. Google's security guidance: "Starting from Android 9, if the device has a lock screen set, then the backup data is not only encrypted, but encrypted with a key not known to Google". — https://developer.android.com/privacy-and-security/risks/backup-best-practices, read 2026-11-26
- [PRIMARY] Size limits conflict: the testing page says D2D "transfer has a much larger data size limit of 2 GB, compared with 2 MB for cloud backup". That contradicts the 25 MB on the Auto Backup page, so it is probably a typo. The GMS transport is "the active cloud backup transport on most devices" and a separate "D2D Transport" handles migration. — https://developer.android.com/identity/data/testingbackup, read 2026-11-26
- [PRIMARY] Cross-platform: "Starting from Android 16 QPR2 (API level 36.1) you can configure Auto Backup for data transfers to and from non-Android devices… The only supported value is `ios`". `<platform-specific-params bundleId teamId contentVersion>` is required. `bundleId` and `teamId` "guarantee that data is only transferred *to* the specified app on the other platform during an export, and that this Android app only imports data *from* that specific app". — autobackup page
- [PRIMARY] Consumer side: the setup flow offers cable, Wi-Fi, or restore "from a Google One backup". It copies "Apps and certain app data" but not "Data from apps that don't use Android backup" or "Apps not from the Google Play Store". "To find backups available to restore, you need to turn on backups on your old device." — https://support.google.com/android/answer/13761358, read 2026-11-26
- [PRIMARY] Naming and settings (2026): the backup is called "Backup by Google One" and lives at Settings > Google services > All services > Backup. It includes "Apps and app data". "Some of your data is end to end encrypted with your device's screen lock PIN, pattern, or password." "Not all apps can back up or restore all settings and data." — https://support.google.com/android/answer/2819582, read 2026-11-26 (no date on the page)
- [PRIMARY] iPhone to Android: the classic wireless and cable flows show "App data: No". Cable moves "Apps available at no charge available on Google Play". "Beginning with Android 17, on some devices, you'll be able to use an upgraded transfer process" (Pixel 8 and newer, some Samsung and Vivo), where "App data" is "Available at app developer's discretion". — https://support.google.com/android/answer/13626960, read 2026-11-26
- [COMMENTARY] 9to5Google, 17 Jun 2026 (Ben Schoon): in the Android 17 flow, "App developers can allow in-app data to transfer between devices". It "Leverages native tools in Android and iOS". The rollout reached a "small percentage" of Android 17 devices, Pixel only at first. — https://9to5google.com/2026/06/17/android-17-iphone-switching-upgrades/, read 2026-11-26
- [PRIMARY] Exclusions Google recommends: files with "device-specific identifiers, either issued by a server or generated on the device", for example FCM tokens. — autobackup page
- Earlier notes in this repo flagged a conflict between Loop's maintainer (2020: uninstall deletes cloud backups) and Google's "restored whenever the app is installed". It is still unresolved in the docs; see Gaps.

### Inferences
- [INFERENCE] With the current manifest and no rules, everything Flutter writes to app-private storage (sqflite database, documents directory, shared_prefs) is in both the cloud backup and D2D. That includes flutter_secure_storage's prefs file, which is Keystore-encrypted and so cannot be decrypted after a restore (Q9). Sources: autobackup "Files that are backed up" and the no-rules default.
- [INFERENCE] With backup off, nothing reaches the cloud, and a setup-time D2D transfer of app data is not documented either way. The separate D2D transport and the rule that D2D "continue[s] to operate even on devices that don't support encryption" suggest D2D does not depend on the cloud backup toggle. Google confirms this explicitly only for restore keys.
- [INFERENCE] App data reaches an iPhone-to-Android switch only with Android 17+ on eligible devices, a `<cross-platform-transfer>` opt-in on the Android side, and presumably a matching opt-in in the iOS app (iOS side not covered here).

## Q8d. What Google recommends in 2026 for "sign the user back in on a new device"

### Takeaway
Google's 2026 answer is Restore Credentials, and Google Play will enforce it. From April 2027 every app with optional or mandatory sign-in must restore the sign-in state automatically on a new device, set up by D2D or from a cloud backup. Compliance is measured by successful restore-key retrieval. Block Store counts only if it was in production by 30 Sep 2026. Apps without accounts or login are explicitly out of scope, and a guest user should arrive on the new phone in the same unauthenticated state. Games are currently exempt. The backup overview now calls Restore Credentials "the recommended way" and no longer lists Block Store, though the Auto Backup page's older tip still points credentials to Block Store.

### Cited Findings
- [PRIMARY] Backup overview, Identity data: "**Restore Credentials**: The recommended way to automatically restore user sign-in state and accounts when users set up a new device, eliminating manual login friction." — https://developer.android.com/guide/topics/data/backup, read 2026-11-26
- [PRIMARY] Credential Manager is "the recommended Jetpack API for credential exchange" and offers "Cross-device credential restore". — https://developer.android.com/identity/credential-manager, read 2026-11-26
- [PRIMARY] Android Developers Blog, 26 Aug 2026 (Raghavendra Hareesh Pottamsetty, GM, Google Play Developer & Monetization): the standard "will require any app supporting user sign-in, optional or mandatory, to automatically restore a user's sign-in state"; "Starting in April 2027, Google Play will require apps to meet the Zero Tap Sign-In requirement" "to maintain full publishing capabilities and optimal visibility in the Play Store"; "games are currently exempt". — https://android-developers.googleblog.com/2026/08/app-quality-memory-optimization-secure-onboarding.html, read 2026-11-26
- [PRIMARY] Play Console technical quality requirements: "apps that support user sign-in (optional or mandatory) must support Zero-Tap Sign-In restoration… either from a device-to-device transfer or cloud backup". "Apps that do not offer user accounts or login functionality are not affected." For signed-out or guest users, "your app should launch in that same unauthenticated state on the new device." Block Store "may be considered compliant but only if the integration was completed and in production on or before September 30, 2026". "Successful user sign in restoration is determined through successful restore key retrieval". Scope is mobile and tablet. Regulated apps can request an exemption. — https://support.google.com/googleplay/android-developer/answer/17492799, read 2026-11-26
- [PRIMARY] Older guidance still live: "To back up user credentials and authentication tokens… use Block Store APIs". — https://developer.android.com/identity/data/autobackup

### Inferences
- [INFERENCE] An app whose only identity is a device key, with no login, is outside the zero-tap requirement. If it later adds an optional account, which the "account later" design implies, that account will fall under the requirement from April 2027. Its compliant Android path would then be Restore Credentials, because a Block Store integration started now misses the 30 Sep 2026 cutoff. Sources: Play Console help, blog.
- [INFERENCE] Restore Credentials could still carry the device-key space even with no account, treating the space as the "account" (Q8b). Google's phrase "same unauthenticated state" concerns signed-out users who have no server identity, so it does not forbid this.

## Q9. Keystore-encrypted data restored without its key (EncryptedSharedPreferences / Tink)

### Takeaway
Android Keystore key material is non-exportable and never leaves the device's secure hardware. Auto Backup or D2D can copy the encrypted prefs file to a new phone or a reinstall, but not the key, so decryption fails. Developers see this as `AEADBadTagException`, `KeyStoreException` or "keyset" errors at startup, sometimes as a crash loop. Google documents this in the EncryptedSharedPreferences class warning ("You should exclude all `EncryptedSharedPreference`s from backup"). In 2026 the Restore Credentials guide also tells apps to exclude "hardware-bound Android Keystore ciphertext" from Auto Backup. security-crypto deprecated all its APIs in 1.1.0-alpha07 (9 Apr 2025), and that became the stable 1.1.0 (30 Jul 2025). The only stated reason is "in favour of existing platform APIs and direct use of Android Keystore", and the class doc points to plain `SharedPreferences`. The usual fixes are to exclude the encrypted file in both rule formats, `<cloud-backup>` and `<device-transfer>`, and to catch the failure, delete the unreadable prefs and start again. Either way, a Keystore-protected secret cannot follow the user through backup.

### Cited Findings
- [PRIMARY] Keystore: "Once keys are in the keystore, you can use them for cryptographic operations, with the key material remaining non-exportable." It prevents "the extraction of the key material from application processes and from the Android device as a whole". With secure hardware, "its key material is never exposed outside of secure hardware". The page itself says nothing explicit about backup. — https://developer.android.com/privacy-and-security/keystore, read 2026-11-26
- [PRIMARY] EncryptedSharedPreferences reference: "This class is deprecated. Use `SharedPreferences` instead." It also warns: "**WARNING**: The preference file should not be backed up with Auto Backup. When restoring the file it is likely the key used to encrypt it will no longer be present. You should exclude all `EncryptedSharedPreference`s from backup using backup rules." `create()` "Throws GeneralSecurityException when a bad master key or keyset has been attempted". — https://developer.android.com/reference/androidx/security/crypto/EncryptedSharedPreferences, read 2026-11-26
- [PRIMARY] Restore Credentials guide (2026), on pairing with Auto Backup: "Exclude raw authentication tokens, hardware-bound Android Keystore ciphertext, and your local `has_synced_restore_credential` marker so stale session state isn't copied onto the new device." — https://developer.android.com/identity/sign-in/restore-credentials, read 2026-11-26
- [PRIMARY] Deprecation timeline: 1.1.0-alpha07 (April 9, 2025) and 1.1.0-beta01 (June 4, 2025), each with the note "Deprecated all APIs in favour of existing platform APIs and direct use of Android Keystore." Stable 1.1.0 shipped July 30, 2025. The release page shows 1.1.0 as the only current version and no newer one; the page's "last updated: September 09, 2026" refers to other artifacts. — https://developer.android.com/jetpack/androidx/releases/security, read 2026-11-26
- [ISSUE] tink-crypto/tink-java #23, "AEADBadTagException AndroidX Jetpack Security startup crash", Jan 2024. The reporter: "The issue is related to backup", reproduced via D2D restore, "even with `allowBackup="false"` the same crash still happens on some devices". Maintainer juergw (labelled "Contributor"; Google affiliation not shown on the page): "The keys stored in keystore are not backed up. So if you restore the backup, you don't have the key anymore, and therefore you can't decrypt anymore… Instead of disabling backup, you can also just exclude the encrypted files… There is nothing else we can do, unfortunately." Later: "It would be enough to delete the shared preferences, there is no need to delete the (newly created) key in keystore." — https://github.com/tink-crypto/tink-java/issues/23, read 2026-11-26
- [ISSUE] google/tink #535 (Aug 2021 to Jan 2024): `KeyStoreException` "exists but is unusable", wrapping `UnrecoverableKeyException`, thrown from `EncryptedSharedPreferences.create`. Later `AEADBadTagException` and "empty keyset". Users report the crash even with `allowBackup="false"`, so key loss also has causes other than backup. — https://github.com/google/tink/issues/535, read 2026-11-26
- [SEARCH] issuetracker.google.com/issues/185219606: a snippet says a Google engineer pointed to the class-doc warning and said "it would be much better to provide an Android backup agent implementation that does the filtering for you". The page needs sign-in and was not read.
- [SEARCH] Many 2026 GitHub fixes of the same pattern ("crash-loop when Auto Backup restores", "recover when the keychain file is restored without its Keystore key"). The usual fix excludes the prefs file in both `data_extraction_rules.xml` `<cloud-backup>` and `backup_rules.xml`, and deletes the store only on that specific decryption exception. Examples: https://github.com/BSoDium/Cron/pull/207, https://github.com/VoltiusApp/voltius/pull/713, https://github.com/ashrafbeshtawi/Casually/issues/16 (titles and snippets only).
- [PRIMARY] Google's general backup security advice: exclude sensitive data, or if that is impossible, require E2EE with `disableIfNoEncryptionCapabilities="true"` (12+) or `requireFlags="clientSideEncryption"` (≤11). If `<device-transfer>` is not set, "all the application data will be transferred during a D2D migration". — https://developer.android.com/privacy-and-security/risks/backup-best-practices, read 2026-11-26

### Inferences
- [INFERENCE] With no backup rules today, the Keystore-encrypted prefs file sits in the default "sharedpref" domain, so cloud backup and D2D both copy it. On the new phone (and on reinstall with restore) it is undecryptable: the device key is lost, and depending on the plugin's error handling the app may fail at start. flutter_secure_storage's own behaviour is covered by another researcher. Sources: autobackup defaults, EncryptedSharedPreferences warning, tink-java #23.
- [INFERENCE] Excluding the file only stops the failure; it does not carry the key across. To make the key follow the user, it has to travel in something not tied to the Keystore. Options: Block Store bytes; a Restore Credentials stand-in; or a plain app-private file in backed-up storage, which relies on Google's backup encryption, end-to-end only on Android 9+ with a screen lock. Google's 2026 guidance discourages the third: "Exclude raw authentication tokens", and use Block Store for credentials. Excluding the encrypted file needs rules in both formats, and on 12+ in both `<cloud-backup>` and `<device-transfer>`.

## Q10. What an Android app can detect

### Takeaway
(i) An ordinary app cannot read the "backup on/off" switch through a public API. `BackupManager.isBackupEnabled()` is not part of the public SDK, and `requestRestore()` has been a no-op since Android 9. The only indirect probes are side effects: Block Store's `isEndToEndEncryptionAvailable()` (Android 9+ and screen lock), or Restore Credentials throwing `E2eeUnavailableException`. That exception covers "no Google Account, backup disabled or no screen lock" without telling them apart. (ii) Whether E2EE is available is readable: through Block Store at any time, and through `getTransportFlags()` (`FLAG_CLIENT_SIDE_ENCRYPTION_ENABLED`, `FLAG_DEVICE_TO_DEVICE_TRANSFER`, and the iOS cross-platform flag from 16 QPR2), but only inside a custom BackupAgent during a backup pass. (iii) No callback reports that a cloud backup was uploaded successfully. A custom agent learns only that a pass started (`onFullBackup`) or that the quota was exceeded (`onQuotaExceeded`), so "your data is backed up as of X" cannot be stated truthfully. (iv) A restore can be detected: by `BackupAgent.onRestoreFinished()`, by a restore key or Block Store bytes on a fresh install, or by a marker kept in a non-backed-up location compared with one kept in a backed-up file.

### Cited Findings
- [PRIMARY] The public BackupManager methods are only `dataChanged()`, `dataChanged(String)` (which needs "android.permission.BACKUP" for other packages), `getUserForAncestralSerialNumber()` and `requestRestore()`. `isBackupEnabled` does not appear. `requestRestore`: "This method was deprecated in API level 28. Applications shouldn't request a restore operation using this method. In Android P and later, this method is a no-op." — https://developer.android.com/reference/android/app/backup/BackupManager, read 2026-11-26
- [SEARCH] The AOSP AIDL says callers of the backup-enabled check "must hold the android.permission.BACKUP permission" (snippet from android.googlesource.com commits; not read).
- [PRIMARY] Transport flags: `FullBackupDataOutput.getTransportFlags()` was "Added in API level 28" and "Returns flags with additional information about the backup transport". BackupAgent constants: `FLAG_CLIENT_SIDE_ENCRYPTION_ENABLED` ("the transport has client-side encryption enabled"), `FLAG_DEVICE_TO_DEVICE_TRANSFER` ("used for a device-to-device transfer"), and `FLAG_CROSS_PLATFORM_DATA_TRANSFER_IOS`. The Auto Backup page spells the last one `FLAG_CROSS_PLATFORM_TRANSFER_IOS`, a doc inconsistency. — https://developer.android.com/reference/android/app/backup/FullBackupDataOutput and https://developer.android.com/reference/android/app/backup/BackupAgent, read 2026-11-26
- [PRIMARY] Callbacks: a custom BackupAgent lets the app "receive notification of backup events, such as `onRestoreFinished()` and `onQuotaExceeded()`. These callback methods are executed even if the app is not running." For file-based backup, keep `android:fullBackupOnly="true"`. During backup and restore "the app's main activity is not automatically launched… the base-class `Application` is instantiated instead of any subclass". — https://developer.android.com/identity/data/autobackup, read 2026-11-26
- [PRIMARY] BackupAgent: restores "are typically performed only when applications are first installed on a device". `onRestoreFinished()`: "The application's restore operation has completed." `onQuotaExceeded`: "Notification that the application's current backup operation causes it to exceed the maximum size permitted by the transport." — BackupAgent reference, read 2026-11-26
- [PRIMARY] E2EE probe: Block Store's `isEndToEndEncryptionAvailable()` "asynchronously determines whether Block Store data backed up to the cloud will be end-to-end encrypted". — BlockstoreClient reference. `E2eeUnavailableException` "occurs if `isCloudBackupEnabled` is `true`, but the user's device doesn't have data backup or end-to-end encryption, such as a screen lock." — https://developer.android.com/identity/sign-in/restore-credentials-implementation, read 2026-11-26
- [PRIMARY] Restore signals: `getCredential` returns a `RestoreCredential` or throws `NoCredentialException`. Google's own pattern keeps a local marker outside backed-up storage (`has_synced_restore_credential`), so a backed-up copy cannot fake "already synced". — implementation page. On a new device, `retrieveBytes` returns the transferred map, or "an empty data map" if nothing was transferred. — BlockstoreClient reference
- [PRIMARY] Manual backup trigger, users only: "go to **Settings > Google > Backup**, click the 'Backup Now' button". For Block Store there is "a 5-minute 'cooldown' period". — https://developer.android.com/identity/block-store

### Inferences
- [INFERENCE] A truthful Android status line can say:
  - whether this install was restored (agent callback or marker comparison);
  - whether cloud backups would be end-to-end encrypted (Block Store probe);
  - whether a Block Store value exists locally and was stored with `shouldBackupToCloud`;
  - whether a restore key was created with cloud backup on or only for D2D (the `E2eeUnavailableException` fallback).
  It cannot say "backup is on" with certainty, and it cannot say "last backed up on…". Sources: the BackupManager reference, the absence of any success callback, and the Block Store and Restore Credentials pages.
- [INFERENCE] `KeyguardManager.isDeviceSecure()` is a public way to check for a screen lock (from general API knowledge; not fetched this session). Combined with Android ≥ 9, it predicts E2EE but not whether backup is on.
- [INFERENCE] Marker pattern: write a random install ID to `getNoBackupFilesDir()` and a copy to a backed-up file. If the backed-up copy exists and differs from the no-backup one, or the no-backup one is missing, this launch follows a restore or D2D. This rests on the documented exclusion of `no_backup` (autobackup page).

## Q11. Is there anything on Android that syncs an app secret live between two devices in use (like iCloud Keychain)?

### Takeaway
No. Android has no silent, live, cross-device store for an arbitrary app secret. Block Store, Restore Credentials and Auto Backup are one-way, one-time carriers that act when a new device is set up or the app is installed. Each device keeps its own backup dataset, and only the latest backup is kept. The only Google mechanism that syncs a credential between devices in use is Google Password Manager, through Credential Manager passwords or passkeys. Saving goes through Credential Manager's system UI (a bottom sheet the user can cancel) and needs a username or ID; passkeys need user verification and Digital Asset Links. Reading back can be auto-selected if only one password exists. Play Games Services Recall does server-linked restore, but only for games.

### Cited Findings
- [PRIMARY] Google Password Manager across devices: you can save passwords and passkeys to your Google Account and use them "to sign in to apps and sites on all your devices where you're signed in with the same account". "Offer to save passwords and passkeys" is on by default and can be turned off. With several accounts, "Android apps prompt you to choose which Google Account to save the password to". — https://support.google.com/accounts/answer/6197437, read 2026-11-26
- [PRIMARY] Saving a password: `CreatePasswordRequest(id = username, password = password)` through `createCredential()`, with the note "manage any errors (for example, if the user cancels the request)". Google "strongly recommend[s] prioritizing… passkeys and Sign in with Google". "Digital Asset Links are required for passkeys and highly recommended for password-based authentication." — https://developer.android.com/identity/passwords, read 2026-11-26. Credential Manager's "bottom sheet UI appears inline to your app's content". — https://developer.android.com/identity/credential-manager, read 2026-11-26
- [PRIMARY] Reading a password back: `GetPasswordOption`'s `isAutoSelectAllowed` is "false by default, allows auto selecting a password if there is only one available". — https://developer.android.com/reference/androidx/credentials/GetPasswordOption, read 2026-11-26
- [PRIMARY] Passkeys: "With the ability to sync passkeys across devices"; sign-in happens "After the user consents to using the passkey by using their device's screen unlock". — https://developer.android.com/identity/passkeys, read 2026-11-26
- [PRIMARY] Auto Backup is not a sync: "Only the most recent backup is stored", with "a backup dataset… for each device", and restore happens "whenever the app is installed". — https://developer.android.com/identity/data/autobackup. Block Store is restored "when the user initiates a restore flow on a new device". — https://developer.android.com/identity/block-store. Restore Credentials works "during the device setup process". — https://developer.android.com/identity/sign-in/restore-credentials. All read 2026-11-26.
- [PRIMARY] The backup overview tells apps that want data on several devices: "You can synchronize app data between Android-powered devices… To learn how, see Transfer data using sync adapters". That means the app's own server sync. — https://developer.android.com/guide/topics/data/backup, read 2026-11-26
- [SEARCH] Play Games Services Recall API: "helps you seamlessly link Google Play Games Services users to their in-game accounts, enabling automatic progress restoration"; the recall token is kept server-side and linked to the PGS profile. — https://developer.android.com/games/pgs/recall (snippet; not read). It is a games SDK.

### Inferences
- [INFERENCE] An app could store the device key as a Credential Manager password with a synthetic ID. It would then sync through Google Password Manager to the user's other Android devices and Chrome. But the save is a visible system prompt the user can refuse, the item shows up in the user's password list as a strange entry, a third-party password manager may be the provider (Android 14+), and Google recommends against passwords anyway. It is neither silent nor tidy. Sources: the passwords, Credential Manager and Google support pages.
- [INFERENCE] The honest answer for "two phones in use" on Android is that the app's own server must do the sync. A device-key space shared between two phones needs the key to reach the second phone once, by Block Store or Restore Credentials during setup, by a QR or link transfer the app builds itself, or by a password-manager entry. After that the server keeps the data in step.
